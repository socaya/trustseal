## Enterprise Project, Programme, Portfolio and Resource Management
**Implementation specification | Version 2.1 proposed | 26 November 2026 | Vitalworks Limited**

Status: Proposed mandatory implementation requirements, not a claim of shipped functionality. Intended repository location: `docs/TrustSeal_Enterprise_Project_Management_Module_Specification.md`.

## 1. Purpose and scope
Transform TrustSeal's existing contract-centric project workspace into a unified enterprise project delivery platform for software, construction, consulting, research, public-sector, health, donor-funded, internal operations and commercial projects. Support predictive, agile and hybrid delivery, single projects and complex multi-programme portfolios. A project may exist without any contract. Preserve the existing contract and document trust capabilities; do not create a second project registry, identity system, signing engine or audit ledger. All requirements below are mandatory for the full release unless explicitly marked configurable or not applicable to a project type.

## 3. Architecture and product boundaries
Use a modular monolith within the existing Flask/SQLAlchemy/PostgreSQL architecture initially. Introduce a project domain blueprint/service/repository/policy/schema package consistent with verified repository conventions. Keep `/projects`, `/projects/<id>` and `/api/projects` backwards compatible; use adapters for legacy clients and additive fields. Use a versioned API for incompatible changes. Reuse shared organization, membership, team, document/version, contract, signature, stamp, notifications, audit, storage, identity, entitlement and worker services. No direct edits to sealed document bytes. Project domain owns planning, allocations, progress, cost control and governance records; accounting/HR/ERP systems remain authoritative for posted ledger, payroll and employee master data where integrated. No payment execution or full ERP replacement is implied.

Hierarchy: Organization > Portfolio > Programme > Project > Workstream/Phase > WBS work package > Task/subtask. Projects may stand alone; portfolio reporting must deduplicate projects with secondary classifications. Deliverables, risks, requirements, resources, contracts, financial transactions and approvals reference the applicable level. Distinguish project lifecycle status from health, work status and contractual status. Use configurable templates, custom fields, project types, calendars, workflows, approval thresholds and numbering sequences with versioned configuration. Store policy snapshots for submitted approvals.

## 4. Lifecycle and stage gates
| Stage | Required records and gate |
|---|---|
| Idea/intake | Request, sponsor, problem, strategic fit, initial cost/benefit; accept for assessment or reject with reason |
| Feasibility | Options, technical/financial feasibility, environmental/social impact if applicable, initial risk and funding; investment decision |
| Initiation | Charter, objectives, scope boundaries, accountable manager, governance and funding authorization |
| Planning | Approved WBS, schedule, resource plan, cost baseline, procurement, quality, risk, communications and M&E plans |
| Mobilization | Team and access, capacity reservation, relevant contracts, readiness checklist, kickoff |
| Execution | Task delivery, progress evidence, time, costs, procurement, communications and continuous controls |
| Acceptance/handover | Accepted deliverables, tests, training, asset/document transfer, outstanding defects and named operational owner |
| Closure | Reconciled costs, contractual disposition, release of resources, closure report, lessons and retention decision |
| Benefits review | Outcome indicators, review dates, benefits owner, sustainability and evaluation evidence |

Lifecycle states: draft, proposed, assessing, authorized, planning, mobilizing, executing, handing_over, closing, closed, archived; additionally on_hold and cancelled with reason, effective date, authority and recovery/disposition plan. Gate state: not_ready, submitted, in_review, approved, rejected, returned, superseded. Gate evaluation is server-side, transactional and records exact evidence versions; exceptions require authorized waiver, rationale, expiry and compensating action. Closed projects read-only except separately authorized benefits updates, archive operations or audited reopen. Monitor and control runs across all stages. No drag-and-drop or PATCH may bypass gates. Templates can collapse stages for small projects but cannot bypass mandatory tenant policies.

## 5. Enterprise module catalogue
Each module below specifies core functionality, owned records, workspace and minimum acceptance. All screens require persistence, validation, permissions, audit, responsive behavior, empty/error/loading states, and tested workflows. Module IDs are stable implementation tracking identifiers.

### PM-01 — Demand, ideas and investment intake
Capture requests from authorized staff or business units using configurable forms; problem, objectives, sponsor, strategic alignment, estimates, alternatives, dependencies and attachments. Triage duplicate requests, score value, urgency, feasibility and risk using versioned weighted criteria; approve, defer, reject or convert to project without re-entry. Maintain intake register and decision history. **Records:** intake, assessment, scoring criterion, decision. **UI:** intake queue, submission wizard, assessment comparison. **Acceptance:** approved intake creates exactly one linked project even on retry; rejected requests retain rationale and cannot silently become active.

### PM-02 — Portfolio and strategic management
Group investments by strategy, business unit, geography, funding and category; prioritize and balance cost, benefit, risk and capacity. Model scenarios with proposed starts, cancellations and funding limits without mutating live plans. Track portfolio dependencies and aggregate approved budget, actuals, benefits and health with drill-down. **Records:** portfolio, membership, strategic objective, scenario, ranking, investment decision. **UI:** portfolio table, roadmap, bubble/priority matrix, scenario comparison. **Acceptance:** scenario publication requires approval; secondary tags never double-count a project and mixed currencies never sum without conversion.

### PM-03 — Programme management
Coordinate related projects, shared outcomes, programme milestones, inter-project dependencies, consolidated governance, shared resources and funding. Manage programme roadmap and escalation paths; benefits may be linked to multiple projects with explicit contribution weights. **Records:** programme, dependency, programme milestone, benefit contribution. **UI:** programme workspace and roadmap. **Acceptance:** delayed upstream project flags affected downstream milestones without automatically changing approved baselines.

### PM-04 — Project registry, charter and governance
Project code, title, sponsor, manager, department, customer, geography, project type, delivery methodology, objectives, boundaries, dates, currency, priority and confidentiality. Maintain charter versions, steering committee, tolerances, governance calendar and delegated authorities. Create from intake, approved template or controlled import. **Records:** existing Project, charter, lifecycle transition, gate, waiver, committee. **UI:** project creation wizard, overview, charter and approval center. **Acceptance:** project authorization requires accountable owner, approved charter and configured funding evidence; code uniqueness enforced per tenant.

### PM-05 — Scope, requirements and traceability
Manage in/out-of-scope items, assumptions, business and technical requirements, acceptance criteria, requirement priority and ownership. Link requirements to WBS, deliverables, tests, changes and signed acceptance. Version scope baseline and produce traceability matrix; flag orphan requirements and untested mandatory criteria. **Records:** requirement, scope item, trace link, scope baseline. **UI:** scope register, requirement detail, matrix. **Acceptance:** approved requirements cannot be overwritten; changes create versions and impact records.

### PM-06 — Work breakdown structure and work packages
Hierarchical WBS with stable codes, workstreams, phases, deliverable-oriented packages, accountable owners, estimates, budgets and completion rules. Reparent, reorder, import/export and clone templates; prevent hierarchy cycles. Distinguish summary packages from executable leaf tasks and avoid counting both. **Records:** WBS node, package, estimate, package baseline. **UI:** editable outline/tree with rollups. **Acceptance:** moving a package preserves links and history; weighted rollups reconcile to leaf work.

### PM-07 — Scheduling, Gantt and critical path
Support planned/forecast/actual dates, working calendars, holidays, time zones, durations, effort, constraints, milestones, leads/lags and FS/SS/FF/SF dependencies. Calculate earliest/latest dates, total/free float, critical path, schedule variance and downstream impact. Support manual vs auto scheduling, baseline comparisons, resource leveling proposals, recurring tasks and cross-project links. **Records:** schedule activity, dependency, calendar, exception, baseline, schedule run. **UI:** synchronized Gantt/grid, timeline, calendar, dependency graph. **Acceptance:** reject dependency cycles; deterministic calendar-aware calculations verified on fixtures; resource leveling previews never silently overwrite baseline; flag infeasible constraints.

### PM-08 — Task and work management
Enhance ProjectTask with identity-backed owner/assignees, WBS, dates, planned/remaining effort, priority, status, checklist, blockers, attachments, comments, dependencies, tags and acceptance evidence. Configurable transitions, subtasks, recurring work, bulk edits and personal work inbox. Multiple contributors but one accountable owner. **Records:** existing task, assignment, checklist, task history. **UI:** list, board, Gantt, task drawer, My Work. **Acceptance:** unauthorized or blocked transition fails; complete requires configured evidence; reopening records reason and updates rollups.

### PM-09 — Agile and hybrid delivery
Backlog, epics, stories, defects, sprint goals, capacity, estimates, planning, daily board, review and retrospective. Track velocity, cycle/lead time, burnup/burndown, WIP limits and release plans. Link stories to requirements and governed milestones; do not equate story points with labor hours or financial value. **Records:** backlog item, sprint, release, estimate, retrospective action. **UI:** backlog, sprint board, release dashboard. **Acceptance:** sprint completion preserves historical scope; carryover and scope changes visible; sprint metrics reproducible from event history.

### PM-10 — Deliverables, milestones and acceptance
Project-wide deliverables independent of contracts; milestones with due date, weight, accountable owner and acceptance criteria. Version submission, reviewer assignment, approve/reject/return, defects, resubmission and sign-off. Link existing ContractDeliverable rather than duplicate contractual acceptance state; signed records retain version/hash/evidence references. **Records:** deliverable, milestone, submission, acceptance, trace link. **UI:** register, review queue, milestone timeline. **Acceptance:** incomplete criteria prevent acceptance unless authorized waiver; changed submission invalidates pending approval; rejection does not count toward earned progress.

### PM-11 — Organization resource pool and skills
Manage employees, consultants, contractors, teams, shared roles, facilities, vehicles, equipment, materials, software licenses and services. People link to organization identities or external resource records; resource records are not login credentials. Skills, certifications, expiry, location, availability, cost/billing rates, employment dates and confidential restrictions. **Records:** resource, skill, qualification, rate version, availability calendar. **UI:** directory, skill matrix, resource profile. **Acceptance:** inactive or expired qualifications are flagged for assignments; rates restricted to authorized finance/resource roles.

### PM-12 — Resource planning, allocation and capacity
Forecast demand by role/skill, period, work package, location and quantity; request, reserve, approve, allocate, replace, release and rebalance resources across projects. Support named and unnamed allocations, fractional FTE, part-time staff, leave, holidays, BAU commitments, overtime policy and resource calendars. Equipment reservations use quantity and maintenance windows; consumables use available stock and issue/return. **Records:** demand, allocation, reservation, calendar exception, capacity snapshot. **UI:** resource planner, heatmap, allocation timeline, demand vs supply, conflicts. **Acceptance:** concurrent allocations cannot exceed capacity under hard-limit policy; soft override requires approval and reason; project closure releases future bookings. Distinguish forecast, tentative, confirmed and actual utilization; no double counting task and project allocation.

**Data model:** timesheet (tenant, resource identity, period, status, version); time_entry (project, work date, WBS/task, contract, cost/fund codes, duration in integer minutes, billable flag, notes, source, optional start/end instants); time_approval_group (project, period, reviewer, state); time_approval_decision; time_rate_snapshot (decimal cost/billing rate, currency, FX, effective date); time_adjustment (original entry, reason, signed delta); time_posting (unique source/version, ledger reference, status); time_policy; time_import_batch. Reconcile identifiers with existing repository conventions. Use tenant-safe composite relationships, optimistic concurrency, database uniqueness and transactional state transitions.

**Calculation rules:** actual effort = approved minutes / 60; labor cost = approved hours × snapshotted cost rate; billable value = eligible approved billable hours × snapshotted billing rate, subject to contract rules; effort variance = actual minus planned hours; utilization = approved productive hours / available working hours × 100; billable ratio = billable approved hours / total approved hours × 100. Zero denominator returns not applicable. Use decimal money and explicit rounding; calculate availability net of applicable leave/holidays, without counting the same reduction twice. Never mix currencies without approved FX conversion.

**Permissions:** contributor edits own draft and submits; project manager reviews only own project groups; resource/line manager views authorized capacity and attendance; finance controls rates, coding, posting and reconciliation; client reviewer sees only explicitly shared certification records; auditor reads authorized historical evidence; administrator configures policy but cannot silently rewrite approved entries.

**UI:** Project > Timesheets (Overview, Team Timesheets, Approvals, Reports); My Work > My Timesheet; Resources > Effort and Utilization; Finance > Labor Costs and Reconciliation. Use shared components and records, compact weekly grid, status filters, clear validation, permission-aware actions and no horizontal page overflow on mobile.

**API:** extend `/api/timesheets` with period listing, draft creation, entries, submit, withdraw, approve/return/reject per group, corrections, lock, import preview/commit, report/export and posting status; expose `/api/projects/<id>/timesheets` as a scoped view over the same service. Use version checks, idempotency keys, pagination, CSRF and authorization. Emit timesheet.submitted, timesheet.returned, timesheet.approved, timesheet.corrected, timesheet.posted and timesheet.locked events.

**Acceptance tests:** cross-project sheet with independent reviewers; self-approval denial; cross-tenant and cross-project denial; overlapping timed entries and duplicate imports rejected; overtime exception approved and audited; rate change mid-period uses correct work-date rates; repeated/concurrent approvals and worker retries produce one ledger posting; correction preserves original and reconciles delta; finance-only rate visibility; signed report version remains verifiable; missing submissions and unposted time block closure; mobile/keyboard entry and export totals verified against database fixtures. All sixteen requirements must be individually tracked in implementation status and verified against real PostgreSQL and end-to-end UI tests.

## 6. Resource and financial calculation rules
- Capacity hours = calendar working hours × employment fraction minus approved leave, holidays and non-project commitments (avoid subtracting holidays twice). Allocation load = confirmed allocated hours / available capacity; actual utilization = approved actual project hours / available capacity. Zero denominator is unavailable, not zero. Report tentative demand separately. Reserve resources in a transaction with deterministic lock ordering; lock overlapping date buckets or use exclusion constraints for exclusive assets. Recheck on calendar/rate changes and surface conflicts.
- Store labor estimates in hours, quantity resources in explicit units and FTE as a ratio; convert FTE to hours using the effective calendar. Do not convert story points into hours automatically. Rates are effective-dated, currency-specific and snapshot on approval. Cost = approved hours × applicable cost rate; billing = billable hours × billing rate, separately. Restrict rate visibility.
- Use PostgreSQL NUMERIC and decimal arithmetic, currency code, original amount, base currency, rate source/date, precision and rounding policy. Do not aggregate mixed currencies without conversion. Unknown FX must yield incomplete totals and a reconciliation exception. Capture historic rates, never recalculate posted amounts from today's rate.
- Budget available = approved applicable budget minus actuals minus outstanding commitments (excluding actual amounts already matched to commitments). Track accruals separately and define whether included in actuals by accounting policy. Receivables and contract revenue never subtract from procurement budget. Proposed/draft contracts are forecast exposure, not committed spending. Signed contract amount is not necessarily total expenditure; map commercial direction and payment schedule. Forecast at completion = actual cost + estimate to complete; distinguish outstanding commitments from ETC to avoid duplication. Budget variance = approved budget minus forecast at completion.
- Earned value (when enabled): PV = time-phased baseline budget of scheduled work; EV = baseline budget × objectively earned completion; AC = approved actual cost for equivalent scope/cutoff. SV = EV − PV; CV = EV − AC; SPI = EV/PV; CPI = EV/AC; EAC = AC + ETC or BAC/CPI only if chosen assumptions hold; VAC = BAC − EAC. Zero denominator unavailable. Keep baseline versions, reporting date and source lineage. Do not calculate EVM for projects lacking approved time-phased cost baseline.
- Work progress = weighted earned completion across leaf packages, not simple task count unless explicitly selected. For milestone-based progress use approved weight and acceptance state; never double-count a deliverable linked to both contract and project. Completed tasks, accepted deliverables and outcome achievement are separate metrics.
- Health policy: dimensions schedule, cost, scope/delivery, risk, resource, quality, compliance and contract. Configurable thresholds (initial examples: forecast cost > approved ceiling red; critical overdue gate red; forecast slip beyond tolerance red; overload amber/red by severity). Overall worst mandatory dimension wins; unknown data cannot silently produce green. Record inputs, reasons, policy version, cutoff and overrides with expiry and authorization. Show historical trends, not only current color.

## 8. Authorization model
Roles are configurable permission bundles, not hardcoded route checks. Combine organization membership, project membership, action permission, record classification, field scope, delegated authority and lifecycle conditions. Default deny. Suggested profiles:

| Role | Permitted scope (subject to policy) |
|---|---|
| Executive/sponsor | Portfolio visibility and assigned investment/gate approvals |
| PMO | Portfolio governance, standards, assurance, cross-project reporting |
| Project manager | Assigned project planning/execution; submit baseline/gates; cannot bypass approval |
| Programme manager | Assigned programme coordination and dependencies |
| Resource manager | Capacity, allocation approval, skills; restricted rates only with separate permission |
| Team lead/member | Assigned work, time, evidence and permitted project context |
| Finance officer/controller | Budget, costs, reconciliation and separately authorized approvals |
| Procurement officer | Requisitions, evaluation, awards under separation of duties |
| Contract/legal officer | Contract workflows and obligations; signature/stamp authority remains separate |
| QA/M&E officer | Quality, indicators, validation and relevant reporting |
| External client/vendor | Explicitly shared records and permitted submission/acceptance actions |
| Auditor | Read-only authorized audit/evidence scope; no operational mutations |
| Tenant administrator | Configuration, access reviews; confidential data access separately granted |

Permission vocabulary: `projects.read/create/update/transition/archive`, `projects.members.manage`, `projects.baselines.submit/approve`, `projects.tasks.assign/update`, `projects.resources.allocate/approve`, `projects.finance.read/rates.read/submit/approve/reconcile`, `projects.procurement.award`, `projects.deliverables.accept`, `projects.reports.export`, `projects.audit.read`, etc. Map to existing permission conventions before implementation. A project ID in a URL is never proof of access; derive tenant from authenticated context and verify every referenced child belongs to the same tenant/project. Validate bulk operations per item. System jobs run with explicit tenant/service identity, not unrestricted user context.

## 10. API and event contracts
Keep existing `/api/projects` endpoints; additive or versioned extensions below are logical route families, not pre-existing routes. Use consistent request schemas, OpenAPI, pagination/cursors, field allowlists, filtering, sorting, request IDs, structured errors and idempotency keys for create/submit/import operations. Use If-Match/version for concurrency-sensitive updates; 409 conflict for stale version, 422 invalid domain data, 403 unauthorized operation or 404 to avoid resource disclosure. Cookie-authenticated mutations require verified CSRF protection, not merely a custom header. Bearer APIs require scoped tokens. Never accept organization ID or approval actor from untrusted payload as authority.

## 11. Production-grade nonfunctional requirements
Proposed initial service targets; validate against real workload and agree with operators before production commitment. Availability 99.9% monthly for core authenticated operations excluding agreed maintenance; p95 ordinary read < 500 ms and write < 1 s server-side under representative load; large exports and schedule recomputation asynchronous with progress and cancel support where safe. Test at 100 concurrent users, 1,000 projects, 100,000 tasks and 10,000 resources per representative large tenant; test multi-tenant isolation and noisy-neighbor workload. These are initial engineering benchmarks, not proven capacity. Define scaling limits, queue concurrency, timeouts, indexes and query budgets. Avoid N+1 queries; aggregate via versioned snapshots/read models when justified; expose freshness.

Security: threat model for finance fraud, privilege escalation, IDOR, cross-tenant leakage, external sharing, malicious imports, formula injection, stored XSS, CSRF, SSRF in integrations, replay, race conditions and evidence substitution. Reuse encryption, private storage, upload scanning, SSO/MFA, audit chain and least-privilege service accounts. Enforce TLS, secret rotation, signed webhooks, content security policy, input validation, export escaping and attachment limits. No sensitive details in logs, metrics labels or notification previews. Conduct dependency scanning, static analysis, security regression and independent penetration testing before enterprise production acceptance. No unsupported certification claims.

Reliability: database backups/PITR, object storage versioning, encrypted offsite backup, documented RPO <= 15 minutes and RTO <= 4 hours as proposed goals, verified restore of database plus linked immutable documents and audit history. Health checks, structured logs, tracing, latency/error/queue metrics, alerts for backlog and failures, runbooks, feature flags, staged deployment and rollback procedures. Use existing monitoring stack; test worker interruption, duplicate messages, partial upload, database outage and expired integrations. Support timezone/currency/localized dates, configurable fiscal calendar and accessible interface. Define retention by record class, legal hold, data export and lawful erasure; project archive is not deletion.

## 14. Implementation tracking and definition of done
Maintain `docs/PROJECT_MANAGEMENT_IMPLEMENTATION_STATUS.md` with one row per atomic requirement: ID, module, requirement, dependency, status, migration, API, UI, permission, test IDs, evidence path, commit and outstanding blocker. Status: not started, in progress, implemented unverified, verified, blocked, or approved not applicable. Coverage = verified mandatory requirements / total applicable mandatory requirements × 100. Track implementation and verification separately; no mapping-only coverage, no counting placeholders, no inflating percentage by excluding blocked requirements. Freeze initial denominator after decomposition; record approved scope changes. Report per-module and overall counts on every batch.

A requirement is verified only when real persistence, business logic, authorization, audit, UI/API, validation, error paths, automated tests and relevant integration evidence exist. Run repository-supported lint/build/test commands locally against real PostgreSQL; inspect actual commands rather than inventing them. Include migration upgrade tests, RLS tests, concurrency tests, browser accessibility and responsive checks, regression of existing contracts/signing, and operational recovery. No dummy data in production paths, mock-only implementations, dead buttons, TODO stubs or claims based on code existence alone.
